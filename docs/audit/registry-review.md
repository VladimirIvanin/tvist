## Required precision in the registry

The added groups are defensible; no new mandatory downgrade was found. Five wording/provenance refinements avoid overstating what ran:

1. **017, [findings.json:910](findings.json#L910), [:916](findings.json#L916): narrow the claim to duplicate IDs.** Recommended title: `Loop clones introduce duplicate form IDs`. Expected: `Cloning valid author content preserves unique IDs in the document tree`. The test measures nine connected inputs with three distinct IDs; it does not click labels, query `label.control`, test screen-reader output, or test copied form values. The duplicate-ID defect is independently grounded in [HTML's tree-wide ID uniqueness requirement](https://html.spec.whatwg.org/multipage/dom.html#the-id-attribute), not an invented Tvist accessibility option. Browser label resolution is deterministic: it uses the first matching labelable element in tree order under the [label algorithm](https://html.spec.whatwg.org/multipage/forms.html#the-label-element). Thus “ambiguous label target” is an integration risk description, not a measured nondeterministic browser behavior. Keep `reproduced` as a DOM-integrity finding; the eventual ID/reference rewriting policy is a design decision.

2. **029, [findings.json:1272](findings.json#L1272): add the exact trigger.** `Explicitly sync main and navigation sliders; reorder the looping navigation slider; instantly select a thumbnail without the normal sync event; click that already-selected original thumbnail.` The problem is the same-selected-thumbnail recovery path after instant navigation, not every original thumbnail click after reorder. SRC-L06 passing normal different-thumbnail clicks is consistent with this finding. Keep this group separate from 003 (the `.sync()` binding exists here) and 024 (the subsequent thumbnail click has its own wrong-index comparison). Suggested review addition: `Thumbs compares captured logical index against reordered DOM activeIndex; the click branch cannot recover the deliberately unsynchronized main selection.`

3. **022, [findings.json:1070](findings.json#L1070): add `roundLengths:false`; the later true phase was not reached.** The 13.5px displacement is one missing gap, not evidence of cumulative subpixel drift or of both rounding modes failing. N=10, perPage=3, width=719.5, gap=13.5 is the actual fixture.

4. **025, [findings.json:1164](findings.json#L1164): attach the completed source evidence and name the failing branch.** In source207, Chromium and Firefox each pass 3/3; WebKit fails 3/3 with leading gaps of **163, 355 and 206 CSS px**. These are `freeSnap:false` observations with autoWidth, center and loop; the `freeSnap:true` phase and the next-navigation check after the failed coverage assertion are not reached in those failing invocations. The absence of momentum-path coverage compensation is source-supported causal evidence, not proof that the defect can only occur in WebKit. The existing older evidence is valid, but it is no longer the best completed cohort.

5. **018, [findings.json:947](findings.json#L947): state the first blocked pair explicitly.** SRC-G11 fails at `loop:true`, from=0 → to=0, following instant selection of the first physical head clone. It does not establish failures for all 36 pairs or the subsequent explicit-clones phase. The current “later all-pairs branches blocked” note is directionally correct; exact first-pair wording prevents readers treating the test's title as completed coverage. G01 fails active cardinality before its coverage assertion. G26 concerns `loading` attributes, not native image decoding.

All new 015–030 records currently omit a `trigger` field. The exact case code and triage documents supply it, so this is not a missing executable reproduction. Adding the above critical qualifiers to the records makes the JSON independently understandable. Registry replay commands intentionally rerun the whole case, not only its failing assertion.
